# E1.1 — Data-driven theme list (foundation)

- **Epic:** E1 · User-Defined Themes
- **Stage:** design  *(awaiting sign-off — hardened by a 4-agent code audit of `www/index.html`)*
- **Platform:** web (then migrate to iOS)
- **Depends on:** —
- **Audit:** workflow `e1.1-design-audit` (5 agents) verified every claim below against the code; line
  numbers are from `www/index.html` and are exact as of this writing.

## 1. Summary
Today the **set** of themes (which themes exist, their keys/names/colours) is a hardcoded `THEMES`
const (`www/index.html:385`). Only the *membership* (which tickers are in each theme) is dynamic
(`state.themeTickers`). This feature makes the **theme list itself data-driven** via a new
`state.themes`, so the whole app — the allocation engine, every tab, the per-theme cap, the version
timeline — works with *any* number and set of themes. It is **invisible and regression-safe**: with
the default 5 themes the app behaves byte-for-behaviour identically to today. This is the plumbing the
later cards (create / rename / delete themes, custom screener, recommendations) build on. **E1.1 adds
no new UI** — it only makes the foundation general and proves it.

## 2. Design

### 2a. Data model
- Keep `THEMES` (the current 5 `{key,name,color,tickers}`, line 385) and the derived
  `DEFAULT_THEME_TICKERS` (line 392) as the **defaults / fallback source**. They do **not** move.
- Add **`state.themes`** (state object, line 417, next to `themeTickers:null`) = array of
  `{key,name,color}`, default **`null`**. `null/empty ⇒ use the `THEMES` defaults.` Membership stays
  in `state.themeTickers`.
- Add two **pure, by-key accessors** (right after line 392):
  - **`themes()`** → `state.themes` if it's a non-empty array, else the static `THEMES`. (Returning
    `THEMES` itself when unset keeps object identity stable; safe because no code compares theme
    objects with `===` — every comparison in the file is on `.key` strings.)
  - **`themeByKey(k)`** → `themes().find(x=>x.key===k)` (for the two lookup sites; callers keep their
    own fallback).
- **Cap becomes nullable.** Change `cap:0.30` (line 414) → **`cap:null`**. The *effective* cap is
  computed at allocation time (see 2d). An explicit user value (set via the cap input) is still a
  number and is honoured verbatim. The user's existing `portfolio.json` already stores `cap:0.30`, so
  **their current book is unchanged**; only a *fresh/reset* portfolio uses the N-adaptive default.

### 2c. Decouple the membership fallback from `THEMES`
`tickersOf(key)` (line 397) falls back to `DEFAULT_THEME_TICKERS[key]`, which is **`undefined`** for
any theme key not in the original 5 — that would throw in `membership().flatMap` / `perTheme().length`
/ `themeMetric`. **Fix:** coalesce to `[]` → `... : (DEFAULT_THEME_TICKERS[key]||[])`. Inert at N=5
(every key resolves); load-bearing for any new key later.

### 2d. N-adaptive per-theme cap
The equal-weight **base is already N-adaptive** in both layers — cross-theme (`applyThemeCap` uses
`n=rows.length`, `1/n` floor at line 584) and within-theme (`perTheme(t)=tickersOf(t.key).length`,
line 404). **So the only engine change is the cap default**, computed where `applyThemeCap` is called
(line 573):

```js
applyThemeCap(rows, state.cap!=null ? state.cap : clamp(1.5/rows.length, 1/rows.length + 1e-9, 1));
```

- `1.5/N` ⇒ **0.30 at N=5** (identical to today), 0.50 at N=3, 0.15 at N=10.
- The `clamp(…, 1/N+ε, 1)` keeps the default just **above** the equal-weight floor (so it never
  silently collapses to equal weight) and inside `[…,1]` at extreme N (the UI's `[1,100]%` clamp at
  line 1485 isn't on this computed path). `applyThemeCap`'s body needs **no** change.
- Surface the *effective* cap in the UI mirror (line 894): show
  `state.cap!=null ? state.cap : 1.5/themes().length`.

### 2e. Persistence / versioning / migration (mirror `themeTickers` exactly)
| Function | Line | Edit |
|---|---|---|
| `snapshotState()` | 622 | append `, themes:deepCopy(state.themes)` |
| `restoreVersion()` | 640 | add `state.themes = s.themes!=null ? deepCopy(s.themes) : null;` |
| `restoreVersion()` pre-build | 634 | add `state.themes=null;` next to `state.themeTickers=null;` |
| `loadPortfolio()` | after 792 | add `if(p.themes)state.themes=p.themes;` |
| `savePortfolio()` | after 805 | add `state.portfolio.themes=state.themes;` |
| `migrateVersions()` | 650 | **no change needed** (restoreVersion's `!=null` guard tolerates missing key, as it does for `themeTickers` today); optional `themes:null` for parity |

Platform writers (`remote/native/web` save/load) serialize the whole object → **no per-platform
change**. Old `portfolio.json` (no `themes`) ⇒ `state.themes` stays `null` ⇒ `themes()` returns the
defaults. **No migration UI.**

### 2f. Keep the sym→theme map fresh
`rebuildThemeOf()` (now reading `themes()`) must run after any mutation of `state.themes` — exactly as
`doSwap` already calls it (line 1361) after changing membership. E1.1 itself has no theme-mutating UI,
but the rule is part of the contract for E1.4–E1.6.

### 2g. Scope boundaries (what E1.1 does **not** do)
- **No CRUD UI** — create (E1.4), rename/recolour (E1.5), delete / delete-all (E1.6).
- **Key-uniqueness validation** of a user-supplied themes array is enforced where themes are *created*
  (E1.4). `themes()` assumes unique keys; duplicates would make `byKey` (574) last-win and double-render.
- **Theme-removal = liquidation** (removed theme's names drop out of `membership()` → sold to $0 on the
  next rebalance, lines 674/1239). This is the same model as a swap; the user-facing **warning in the
  rebalance preview** is **E1.6**. E1.1 only ensures the plumbing handles it without crashing.
- **Cosmetic copy** that hardcodes "five themes" / "5 names" (lines 308, 371, 931, 937, 1041–1042) is
  optional polish — does not affect math. Defer or fold in opportunistically.
- **Custom-theme colour picker** is E1.4; E1.1 colours come from the defaults.

## 3. Acceptance criteria
- [ ] **Regression gate.** With `state.themes=null`, `state.cap=null` (and an existing book with the
  saved `cap:0.30`), every numeric output — allocation %, per-theme cap, per-name targets, holdings
  table, version snapshots — is **byte-for-behaviour identical** to pre-E1.1 at the default 5 themes.
- [ ] **Old portfolio loads clean.** A `portfolio.json` saved before E1.1 (no `themes` key, `cap:0.30`)
  loads, rebalances, and renders identically (`themes()` → defaults; cap honoured verbatim).
- [ ] **Atomic conversion.** All 14 `THEMES` sites converted in one pass; no view reads static `THEMES`
  while `themes()` is non-null (no `alloc.byKey[t.key]` throw).
- [ ] **Persists & restores.** `state.themes` saves to `portfolio.json` and is restored by undo / redo
  / revert (it's in the version snapshot), in lock-step with `themeTickers`.
- [ ] **Generality proof.** Injecting a modified `state.themes` in the console — **N=3** and **N=7**, plus
  a rename + recolour — makes every tab, the engine, and the rebalancer adapt (N-derived cap &
  equal-weight, the sym→theme map, the screener swatch/swap) with no errors, then reverting restores 5.
- [ ] **Cap precedence.** `state.cap==null` → effective = `clamp(1.5/N, 1/N+ε, 1)`; `state.cap==number`
  → used verbatim. Verify at **N=3** (1.5/3=0.50, above the 1/3 floor) and **N=10** (0.15) the
  equalize branch (line 584) does **not** fire unexpectedly.
- [ ] **No direct live-list iteration of `THEMES` remains** (only as the default inside `themes()`).

## 6. iOS migration notes
- Pure `www/index.html` change → Mac runs `npx cap sync ios`. **No native / Swift change.** The
  `.native` skin reuses the same renderers and `computeAllocation` rows, so it adapts automatically.
- The new persisted `themes` field flows through the **same** portfolio save/load — `localStorage`
  on-device and the LAN-sync `/api/portfolio` path — with no extra work (the platform writers
  serialize the whole `state.portfolio`). The Mac only needs to confirm the round-trip on-device.
